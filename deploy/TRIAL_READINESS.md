## 真实扩缩容结果

同时发出 120 个 IO 请求（先等待 10 秒，再内部调用 Compute）和 8 个直接 Compute 请求，共 128 个请求，全部成功且结果正确。

| 指标 | 观察结果 |
| --- | --- |
| IO Actor | 从 2 个扩到 4 个；空闲约 5 分钟后缩到 1 个 |
| 活跃 default Worker 节点 | 从 2 个扩到 10 个，随后逐步降到 4 个、3 个 |
| 压测结束时的 lease | active_io、running_leases、reserved_leases 均为 0 |
| IO 延迟 | 最小 25.26 秒，中位数 26.21 秒，P95 26.37 秒，最大 26.42 秒 |
| 直接 Compute 延迟 | 最小 2.28 秒，中位数 3.86 秒，P95 和最大值 28.68 秒 |

节点数来自 Ray 的存活节点和 worker-pool 标签，不是 Kubernetes Pod 查询。后续热更新和重启回归再次产生流量，Actor 又创建 Warm 副本，因此上述缩到 1 个是空闲阶段的实际观察，不代表测试结束时始终保持 1 个。

当前多余 Actor 的空闲回收为 300 秒，最后一个 Warm Actor 为 1800 秒；集群配置中的 Worker 空闲回收为 300 秒，两层回收时间会叠加。本轮验证了自然扩容和部分自然缩容，没有等待最后一个 Actor 的 30 分钟自然回收。缩到零和忙碌 lease 不被误回收的逻辑由自动化测试覆盖。

128 个短请求曾将 Worker 扩到上限 10 个，说明伸缩有效，但突发流量仍有较高的节点扩容和环境预热成本。试运行前应结合机器资源预算检查 maxReplicas、内部 Compute 并发及排队限额；本轮未修改这些配置。

修复后追加 48 个 IO 请求（等待 2 秒，再内部调用 Compute）和 4 个直接 Compute 请求，共 52 个请求全部成功。已预热状态下延迟最小 1.21 秒、中位数 2.96 秒、最大 3.53 秒；结束时 2 个 Actor 在线，active_io、running_leases、reserved_leases 均为 0。这是预热后的并发回归，不替代首轮冷启动扩缩容结果。

## 已修复并回归的问题

### REST 严格校验接口契约

REST 入口在鉴权和接口解析后、记录调用及派发 Ray 前，根据不可变 Hook Manifest 递归校验必填字段、未知字段、类型、整数范围和嵌套结构，不做隐式类型转换。无效参数返回 HTTP 422，错误信息包含字段路径、不包含输入值；业务执行失败继续采用原有状态返回协议。

真实请求验证了缺少参数、额外参数、字符串错类型、Int32 越界、Bool 冒充整数、Float 冒充整数、嵌套字段缺失 7 种情况，均返回 422，未新增调用记录。`add(2147483647, 1)` 的返回值越界被标记为 FAILED，result 为 null，仍保留执行日志。

本次 REST 校验覆盖 JSON 原生类型。Bytes、Date、Datetime、DatetimeTz 和 ArrowTable 未增加 JSON 编解码协议，应使用 gRPC；真实 gRPC 类型回归仍全部通过。

实现位置为 `src/pyscripts/contracts/validation.py` 和 `src/pyscripts/api.py` 的 `invoke`。

### 按 lease 取消运行中的 IO

Actor 按 lease 跟踪执行协程，取消只作用于对应请求并等待清理，不杀死共享 Actor；内部 Compute 随父任务级联取消。调度器等待取消确认，清理超时上限为 5 秒。HTTP 中间件取消时，Actor 取消和数据库收尾受到清理保护，调用记录不会停留在 RUNNING。

真实集群中，等待 60 秒的 IO 使用 0.8 秒 gRPC deadline，客户端按时收到 DEADLINE_EXCEEDED；再等待 1 秒时 active_io 和 running_leases 已为 0，数据库为 CANCELLED。同 Actor 上并发的另一 IO 正常返回 43，结束后 lease 全部归零。自动化测试另验证内部 Compute 取消、未开始 reservation 取消，以及 HTTP 取消后的数据库收尾。

共享代码初始化与单次请求取消分开，取消一个等待者不会中断其他请求的加载。Actor 协议命名升级为 v9，旧协议 Actor 排空后退出，新请求使用新实现；首次扫描时仍忙碌的旧 Actor 会在后续扫描中继续检查并回收，已有回归测试。

取消依赖业务协程遵守 asyncio 取消语义；阻塞事件循环或主动吞掉取消的业务代码不能保证及时停止。本次没有增加 HTTP 客户端断开连接的主动检测机制。

### 环境退休启动恢复和周期重试

启动立即扫描数据库 RETIRING 版本，按版本去重调度，最多同时执行 4 个退休任务。失败或超时保持 RETIRING，由周期扫描重试；新增配置 `PYSCRIPTS_RUNTIME_PROFILE_RETIREMENT_RETRY_SECONDS`，默认 15 秒。退休前后均检查活动版本、服务引用和在途执行，排空当前及旧协议 Actor；Actor 状态查询异常不会被当作空闲。

真实重启后，原先滞留的 `test@v1`、`test@v2`、`test@v3` 自动转为 RETIRED，`test@v4` 保持 ACTIVE。回归测试模拟关闭时中断退休、重启恢复、一次超时和一次异常后成功，且同版本未出现并发重复退休。忙碌旧 Actor 和无响应 RPC 也有回归覆盖。

本次持久恢复范围是环境退休，不代表所有 VALIDATING、发布中或异常断电留下的调用状态都有完整恢复机制。

## 部署和验收边界

- Dockerfile 的前端阶段构建成功，但 Python 基础镜像从 Docker Hub 拉取时网络超时，Podman 构建退出失败。Compose provider 也未能在限定时间内获取，因此尚未验证完整容器启动、健康检查和重启恢复。
- 管理功能通过真实鉴权中间件检查，诊断会话由本地管理员会话密钥和数据库 session version 签发。没有重置密码；使用当前密码的人工网页登录及页面交互仍需验收。
- 控制面和集群 Python 小版本分别为 3.12.3、3.12.13，Ray 给出 patch 版本不同警告；本轮调用通过，部署时仍建议保持版本一致。
- `poll` 当前只保存配置，没有周期 Git 检查任务。试运行应使用手动发布或 Webhook。
- Webhook 执行队列尚未持久化，进程重启可能丢失已接收的通知。需要允许重新投递，并注意 URL 中的 webhook 密钥会进入常规访问日志。
- 控制面保持单实例、单 Uvicorn worker；不能据此认定支持多副本协调或高可用。健康检查成功也不代表 Ray、对象存储始终可用。
- 仅执行受信任代码；运行环境和模块隔离不是安全沙箱。Ray Client 和 Dashboard 不应公开到互联网。对外提供管理端和调用接口前，应配置 TLS、网络访问限制及数据库和对象存储备份。
